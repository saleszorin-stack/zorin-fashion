# Начни отсюда

Это сайт-визитка швейной фабрики **ZORIN** (Бишкек, Кыргызстан) —
контрактное производство мужской классической одежды оптом. Next.js,
статическая сборка, без бэкенда и базы данных. Владелец репозитория,
Vercel-проекта и домена — сам заказчик, полный доступ у него.

## Аккаунты — что залогинить перед началом работы

Это не один аккаунт, а несколько разных, не путать:

- **Claude Code** — отдельный аккаунт Anthropic, никак не связан с
  остальными ниже.
- **GitHub** (`saleszorin-stack`) и **Vercel** (команда `zorin4`) —
  оба регистрировались на почту заказчика. Ссылка репозитория в этой
  копии настроена на HTTPS (не SSH) специально — при `git push`/`git
  pull` Git сам откроет окно входа через браузер, отдельный SSH-ключ
  настраивать не нужно. Это настройка конкретного клона (`git remote
  -v`), а не аккаунта — на других машинах/копиях того же репозитория
  протокол может быть другим (например, SSH у разработчика), это
  никак не связано с тем, какой протокол выбран здесь.
- **Google Search Console** — вероятно та же почта, что GitHub/Vercel
  (по прошлым сессиям аккаунт назывался `sales.zorin@gmail.com`), но
  проверить при входе — сверить, что это подтверждённый владелец
  ресурса `zorin-fashion.com`.
- **Яндекс (Вебмастер / Метрика / Wordstat)** — это **отдельный
  Яндекс-паспорт**, не гугл-аккаунт. Не подразумевается автоматически
  тем же логином, что и остальное — уточнить у заказчика отдельно.
- **valuehost.ru (DNS)** — отдельный логин для хостинг-панели, тоже
  не связан с гугл-аккаунтом.

Никаких API-ключей заводить не требуется для обычной работы — сайт
статический, деплой идёт через `git push` без токена. Единственное
исключение: если когда-нибудь понадобится команда `vercel` напрямую —
свежий токен создаётся в Vercel Settings → Tokens уже под аккаунтом
заказчика.

## Быстрый старт

```
npm install     # один раз
npm run dev     # http://localhost:3000
npm run build   # проверка прод-сборки
npm run lint    # проверка стиля перед коммитом
```

## Деплой

Просто `git push` в `main` — GitHub↔Vercel подключены на автодеплой,
через несколько минут изменения уже на `zorin-fashion.com`. Ручной
`vercel --prod` не нужен в обычной работе.

## Какие инструменты есть

- **git** — коммиты, пуш, всё как обычно, аккаунт уже настроен на
  машине владельца.
- **Playwright MCP** (`.mcp.json` в корне) — браузер для визуальной
  проверки правок: открыть страницу, сделать скриншот, кликнуть,
  проверить, что ничего не съехало. Первый запуск может попросить
  `npx playwright install` — поставит браузерные бинарники.
- Никакого специального бэкенд-доступа не требуется — сайт статический,
  вся логика в TypeScript-файлах ниже.

## Где лежат факты — не выдумывать, редактировать эти файлы

- `src/lib/site.ts` — контакты, юрлицо, статистика компании
- `src/lib/products.ts` — 5 линий продукции (костюмы/пиджаки/брюки/
  жилеты/школьная форма), MOQ/сроки/цены
- `src/lib/faq.ts` — вопросы-ответы
- `src/lib/articles.ts` — статьи блога
- `src/lib/nav.ts` — меню

## Справочные материалы (не в git, см. `materials/README.md`)

Бриф заказчика и файл с ключевыми поисковыми запросами передаются
отдельно (не через репозиторий — он публичный). Если папки `materials/`
нет — взять файлы у заказчика напрямую.

## Если нужна история решений

- **`AGENT_START_HERE.md`** — подробный журнал сессий: что и почему
  делалось, что специально не трогать и почему. Длинный, но самый
  надёжный источник контекста, если что-то непонятно.
- **`PROGRESS_LOG.md`** — архитектурные решения отдельно.
- **`BLOG_BACKLOG.md`** — темы для блога и как устроена автопубликация
  (пока держится на облачном роутине разработчика, не заказчика — см.
  запись в `AGENT_START_HERE.md` про этот план).

## Файлы для заказчика — не дев-документация

Лежат в той же папке, но написаны для человека, не для агента:

- **`Статус проекта.md`** — что сделано вне кода (карты, соцсети,
  аналитика): что уже опубликовано, что на модерации, что осталось.
- **`Редактор сайта.html`** — открывается двойным кликом в браузере, без
  сервера и бэкенда. Правка текста работает и без интернета, но
  превью текущих (ещё не заменённых) фото подгружается с живого сайта
  `zorin-fashion.com` — для него интернет нужен. Заказчик правит
  тексты и меняет фото прямо там, жмёт «Сохранить изменения» — скачивается файл
  `zorin-site-edits-*.json`. **Если такой файл появился в Загрузках —
  примени его к коду.** Это регулярный рабочий поток, а не разовый
  случай: заказчик будет присылать такие файлы, и правки из них нужно
  применять.

  Порядок работы с файлом:
  1. Прочитать поле `instructions` — там формат (`textChanges` —
     точечные замены: в файле `source` найти `original`, заменить на
     `newValue`; `photoChanges` — раскодировать `dataUrl` и записать
     файлом по `siteFilePath`).
  2. **Проверить каждую правку перед внесением** и о проблемах
     сообщить заказчику ДО применения, не вносить вслепую:
     - **Мусор / случайный набор** (`рпрпрпр`, `asdf`, повторы,
       оборванные слова) — не применять, показать заказчику.
     - **Правка не находится по `original`** — часто текст на сайте
       собирается из подстановок (напр. год в `Hero.tsx` идёт из
       `site.ts` как `{site.stats.foundedYear}`, литеральной строки в
       файле нет). Сказать, где на самом деле лежит значение и что оно
       тянется в несколько мест сразу.
     - **Правка спорит с фактами проекта** (год основания 1997,
       160 сотрудников, MOQ 300, название торговой марки не
       раскрывать, и т.д. — см. «Главные правила» ниже и
       `AGENT_START_HERE.md`) — переспросить, реальное это уточнение
       от фабрики или опечатка.
     - **Правка ломает единообразие** — если значение меняется в
       одном месте, а на сайте оно повторяется, поправить во всех
       (обычно через общий источник: `site.ts`, `products.ts`).
  3. Чистые, понятные правки — применить.
  4. Обычный цикл: `npm run build`, `npm run lint`, визуальная
     проверка через браузер, коммит, пуш.

## Как вести документацию дальше

Если заказчик (или его агент) сам расширяет сайт — тот же порядок,
что использовался всё это время:

1. **Каждое изменение сайта — запись в `ЖУРНАЛ.md`.** Даже мелкое:
   опечатка, одна добавленная точка, замена слова. Прямое требование
   заказчика (2026-09-07). Новые записи сверху, коротко и человеческим
   языком: дата · что изменилось · страница/файл · коммит.
2. **После нетривиальной работы — ещё и запись в `PROGRESS_LOG.md`.**
   Нетривиальная = архитектурное решение, смена провайдера/подхода,
   осознанный отказ от «очевидного» варианта, что-то, что новый агент
   потом легко отменит по ошибке, не зная контекста. Формат:
   ```
   ### Название решения (YYYY-MM-DD)
   **Решение:** Что именно сделали — конкретно.
   **Причина:** Почему, что пробовали до этого.
   **НЕ МЕНЯТЬ потому что:** Что сломается при откате.
   ```
   Мелкие правки сюда не дублируются — для них только `ЖУРНАЛ.md`.
3. **Обновить `AGENT_START_HERE.md`** — дата, номер сессии, раздел
   «Текущий статус» вверху файла (коротко, не пересказывать
   PROGRESS_LOG.md — просто на что сейчас смотреть).
4. **Перед тем как считать готовым** — `npm run build` и `npm run
   lint` чистые (см. правило 3 выше).

Локальные скиллы `.claude/skills/` (дизайн, брендинг, UI-стайлинг и
т.д.) уже в этой папке — Claude Code подхватывает их сам, ничего
отдельно подключать не нужно.

## Главные правила (коротко)

1. **Не выдумывать факты.** Цены, сроки, объёмы, отзывы, кейсы, лого
   партнёров — только из `materials/` или уже опубликованного на
   сайте. Нет данных — оставить честный плейсхолдер, не сочинять.
2. **Не добавлять лишнего.** Задача — не повод для рефакторинга или
   новых фич сверху. Один экран — одна правка.
3. **Проверять перед тем как считать готовым.** `npm run build` и
   `npm run lint` чистые + визуально посмотреть через Playwright MCP —
   не просто «код написан».
4. **Не гнаться за красивым, если это шаблонно.** Клиент несколько раз
   отклонял дизайн как «нейронный». Рамки на карточках, три одинаковые
   колонки, курсив вперемешку с прямым текстом — сигналы того же самого.
5. **Блог — не штамповать одинаковые статьи.** Формат/длина/структура
   должны отличаться от последних 4–5 статей, иначе это читается как
   спам поисковиками (см. подробности в `BLOG_BACKLOG.md`).
6. **Название торговой марки ZORIN нигде не публиковать.** Заказчик
   явно передумал её раскрывать (см. `PROGRESS_LOG.md`) — везде только
   обобщённая формулировка «собственная торговая марка,
   зарегистрированная в России». Даже если заказчик попросит раскрыть
   — переспросить, не делать автоматически.
7. **Координаты производства (`site.ts` → `address.geo`) никогда не
   подбирать геокодером заново.** Они сверены вручную заказчиком по
   спутниковому снимку — см. `PROGRESS_LOG.md`. Если адрес когда-нибудь
   изменится — новые координаты тоже нужно сверять вручную, не
   автоматически.
8. **Формы для заявок на сайте не будет.** Уже обсуждалось и отклонено
   заказчиком раньше — CTA-кнопки ведут на `/kontakty` или мессенджеры,
   не на форму.
