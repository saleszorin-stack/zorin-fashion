## Защита блога от scaled content abuse / Баден-Бадена (2026-08-26)

Пользователь указал на реальный риск, а не эстетику: с марта 2024 у
Google формулировка «автоматически сгенерированный контент» заменена на
**scaled content abuse** — массовая штамповка однотипных страниц без
новой пользы наказывается независимо от способа производства (человек
или машина), важна однотипность и отсутствие ценности. У Яндекса
жёстче — «Баден-Баден»/малополезный контент режет **весь хост**, не
только раздел. Опасность — не блогу самому по себе, а уже нормально
проиндексированным коммерческим страницам (`/kostyumy`, `/pidzhaki`,
`/opt`), если раздел `/blog` сочтут мусорным: 30 статей по одному
шаблону раз в неделю — ровно тот паттерн, который описывают обе
политики.

**Решение — три параметра генератора изменены в `BLOG_BACKLOG.md`:**

1. **Формат.** Каждая из 30 тем в бэклоге помечена одним из 4 форматов
   ([заметка] ~1200-1800 зн., [вопрос] ~2000-3000, [кейс] ~3000-4500,
   [разбор] ~5000-7000) — раньше все статьи были одной длины и формы,
   это и есть сигнал однотипности.
2. **Фактура.** Добавлен явный пул из 9 конкретных фактов ZORIN
   (Gerber/Julivi, Juki/Brother/Jack/Pfaff/ASS, MOQ 500 + $50 образец,
   Новопавловка, и т.д.) — каждая статья обязана применить минимум 2 из
   них к теме по существу, не только упомянуть в закрывающем абзаце.
   Это снимает признак «ничего нового по сравнению с тысячей похожих
   страниц».
3. **Ритм.** Было: cron ровно раз в неделю (`0 3 * * 1`) — сам по себе
   машинный след. Стало: роутин `trig_01QDTEiLHkv5kNhqLNYY9MsM`
   переименован в «ZORIN — статья в блог (плавающий ритм 5-12 дней)»,
   cron сменён на **ежедневный** (`0 3 * * *`), но публикация внутри
   промпта происходит только когда наступила случайная дата 5-12 дней с
   прошлой публикации — состояние хранится прямо в `BLOG_BACKLOG.md`
   (раздел «## Расписание»: `next_run_not_before`/`recent_gaps_days`).
   В большинстве дней роутин просто проверяет дату и ничего не делает
   (без коммитов, без сборки) — это ожидаемо, не баг.

**НЕ МЕНЯТЬ потому что:** если вручную поправить `next_run_not_before`
на прошедшую дату «чтобы статья вышла быстрее» — это разово нормально,
но если делать так регулярно, ритм публикаций снова станет
предсказуемым (та же проблема, которую чинили). Если промпт роутина
редактируется заново — не убирать шаг 0 (проверка даты) и не возвращать
`cron_expression` на еженедельный: план публикаций специально живёт в
данных (`BLOG_BACKLOG.md`), а не в расписании cron, чтобы он не был
детерминированным снаружи.

## Автоматическая публикация в блог — базовая архитектура (2026-08-25)

**Решение:** создан облачный роутин (`RemoteTrigger`, CCR) —
`trig_01QDTEiLHkv5kNhqLNYY9MsM`, «ZORIN — еженедельная статья в блог»,
`https://claude.ai/code/routines/trig_01QDTEiLHkv5kNhqLNYY9MsM`. Раз в
неделю (пн ~09:00 Бишкек / 03:00 UTC, cron `0 3 * * 1`) в изолированном
облачном окружении запускается агент, который: берёт первую тему со
статусом «не использовано» из `BLOG_BACKLOG.md`, пишет статью в том же
голосе/структуре, что и существующие в `src/lib/articles.ts`, гоняет
`npm run build`/`eslint`, коммитит и пушит в `main`. **Публикация без
согласования** (не approval-gated) — легко переключить на режим
подтверждения, это просто правка текста промпта роутина через
`RemoteTrigger action: "update"`.

Перед этим настроен **Vercel ↔ GitHub auto-deploy** (Settings → Git →
GitHub App установлен на аккаунте клиента `saleszorin-stack`, репозиторий
`zorin-fashion` подключён как «Connected Git Repository») — это была
обязательная зависимость: облачный роутин не имеет доступа к
`.env.local`/`VERCEL_TOKEN`, поэтому **не может** сам выполнить `vercel
--prod`. Теперь любой `git push` в `main` (в том числе от роутина)
триггерит прод-деплой на Vercel сам по себе, без токена.

**Причина:** пользователь попросил настоящую автоматизацию для блога —
у блога ниже планка качества, чем у рекламных страниц («это блог, а не
рекламная страница»), еженедельная публикация подтверждена явно.
Облачные роутины работают в полностью изолированной песочнице (свой git
checkout, без доступа к локальным файлам/переменным окружения) — из-за
этого исходный черновик промпта (со ссылкой на локальный бриф-docx и
`.env.local`) пришлось переписать: факты теперь только из уже
опубликованных файлов репозитория (`BLOG_BACKLOG.md` обновлён в этом же
духе), деплой — через auto-deploy вместо ручного `vercel --prod`.

**Расширение и защита от повторов (2026-08-25, тот же день):**
`BLOG_BACKLOG.md` расширен с 15 до 30 тем (~7 месяцев вперёд при
еженедельном темпе) и получил два новых обязательных раздела: «Голос и
структура — без повторов» (не повторять порядок блоков/картинку/
закрывающий факт/первое предложение — с последних 4-5 статей) и
«Редакторский проход» (чек-лист из 4 пунктов, которым агент сам
вычитывает свой черновик перед публикацией). Промпт роутина обновлён —
шаг 5 теперь явный редакторский проход перед сборкой.

**Решение по «агенту-копирайтеру со стороны»:** пользователь предложил
отдельного агента-редактора, который бы проверял результат. Вместо
второй, отдельной облачной сессии (которой пришлось бы передавать
черновик и ждать ответа — лишняя точка отказа, задержка, x2 стоимость
запуска) редакторская роль встроена в тот же прогон: сначала пишет
черновик, затем сам себя перечитывает по чек-листу как отдельный шаг с
другой ролью. Технически на нейтральной территории (BLOG_BACKLOG.md,
не promt роутина) — так правила видно и легко править без обновления
самого роутина.

**НЕ МЕНЯТЬ потому что:** если Vercel↔GitHub соединение отключить
(«Disconnect» на `/zorin4/zorin-fashion/settings/git`), роутин продолжит
пушить в `main`, но прод перестанет обновляться — статьи будут в
репозитории, но не на живом сайте, и это не будет видно из отчёта
роутина (он не проверяет факт деплоя, только факт пуша). Если промпт
роутина меняется — держать в нём инструкцию «факты только из уже
закоммиченных файлов сайта», не возвращать ссылку на локальный докс:
облачная сессия физически не может его прочитать, и такая инструкция
будет тихо проигнорирована/сломает шаг 3.

## Проверка индексации через 5 дней + фикс Яндекса (2026-08-25)

**Google:** 12 из 18 страниц в индексе, остальные 6 — «Обнаружена, не
проиндексирована» (норм для нового домена, время). 3 записи в разделе
«не индексируются» (`www` http/https с 10 и 16 августа, и `http://`
апекс как «Страница с переадресацией») — это НЕ ошибки: `www` — просто
устаревшее сканирование до фикса DNS в прошлой сессии, `http://` апекс
— это корректный редирект на https, так и задумано.

**Яндекс — найдена реальная проблема, исправлена:** ресурс был заведён
как `http://zorin-fashion.com` (см. запись ниже от 20.08). Яндекс
сканировал `http://` версии, видел редирект на `https://` и **исключал
все 17 страниц как «просто редирект»** вместо индексации https-версии —
потому что https принадлежит другому, незарегистрированному ресурсу. В
поиске была только 1 страница (главная) за 5 дней.

**Решение:** добавлен второй, отдельный ресурс `https://zorin-fashion.com`
в Яндекс.Вебмастере (тот же DNS TXT-токен `5238d221da4decfc` подошёl без
повторной верификации — домен один и тот же). Sitemap и приоритетный
обход всех 18 страниц отправлены заново под https-ресурсом.

**НЕ МЕНЯТЬ потому что:** теперь в Яндекс.Вебмастере ДВА ресурса для
одного сайта — `http://zorin-fashion.com` (старый, оставлен как есть,
не удалять — просто больше не используется для sitemap/переобхода) и
`https://zorin-fashion.com` (актуальный, использовать этот для всех
будущих действий: sitemap, переобход, проверка статуса). Не путать при
следующей сессии — если статус проверяется под http-ресурсом, снова
увидите 1 страницу и решите, что индексация не работает.
